# Date-wise tutor timetables: findings, schema proposal and fixture plan

Status: **proposal only.** Nothing in this document has been run. No database was written (the staging database was read in a read-only session to take the inventory below). No migration file was added, nothing was pushed or deployed, and no seed or permission was touched.

Companion file: [TUTOR_TIMETABLE_FIXTURE_PREVIEW.md](TUTOR_TIMETABLE_FIXTURE_PREVIEW.md), the full dry run of the proposed data, generated by `apps/api/scripts/tutor-timetable-fixture/preview.ts`.

## 1. Can the current schema hold date-wise timetables?

**No.** It holds weekly hours and recurring bookings, but not dates. The gaps are specific.

| Need | What exists | Verdict |
|---|---|---|
| Tutor, subjects, levels | `tutor_profiles`, `tutor_subjects`, `tutor_grades` | Supported. Levels are per tutor, not per subject (fine for this data). |
| Weekly working hours, several ranges a day, non-working days | `tutor_availability_slots` | Supported. |
| Breaks | The gap between two ranges on one day | Supported, with no stored label. |
| Leave | `employee_leave_requests` (dates as text, status APPROVED) | Supported for whole days. Tutors are employees, so approved leave can be read. |
| Recurring bookings: weekly, bi-weekly, monthly | `mentoring_tutor_assignment_sessions` (added in the last release) | Supported as a pattern, but **with no start date**. |
| Exact-date bookings | `demo_sessions` and `demo_session_tutor_assignments` (demos only), `tutor_class_records` (empty, no link to a class) | Not for ongoing classes. |
| Public holidays | None | **Missing.** |
| Date-specific extra hours, blocked time, a special day off | None | **Missing.** |
| Cancelling or rescheduling one occurrence | None for recurring classes | **Missing.** |
| A dated class table (class sessions) | None. `student_attendances.session_id` and `tutor_class_records.session_id` are plain text that point at nothing. | **Missing.** |
| A tutor calendar screen | None. There is no tutor profile page. | **Missing.** |

The most important gap: a recurring booking says "bi-weekly, Week 1" but nothing says which calendar week is Week 1. Today the checker assumes the same weeks for every student, which is why "November 9" cannot be answered exactly yet.

## 2. Proposed schema (additive, nothing dropped or rewritten)

```sql
-- Proposed, not applied.

-- 1. Dates that change a tutor's weekly pattern. tutor_profile_id NULL means the whole organisation (a public holiday).
CREATE TYPE "TutorExceptionKind" AS ENUM ('HOLIDAY', 'DAY_OFF', 'EXTRA_HOURS', 'BLOCKED');
CREATE TABLE "tutor_availability_exceptions" (
  "id" TEXT PRIMARY KEY,
  "tutor_profile_id" TEXT,                       -- NULL = everyone
  "date" DATE NOT NULL,
  "kind" "TutorExceptionKind" NOT NULL,
  "start_minute" INTEGER, "end_minute" INTEGER,  -- NULL = the whole day (HOLIDAY, DAY_OFF); required for EXTRA_HOURS and BLOCKED
  "note" TEXT NOT NULL,
  "created_by_user_id" TEXT NOT NULL,
  "created_at" TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP,
  "is_active" BOOLEAN NOT NULL DEFAULT TRUE,
  "deactivated_at" TIMESTAMP(3),
  CHECK (("start_minute" IS NULL AND "end_minute" IS NULL) OR ("start_minute" >= 0 AND "end_minute" <= 1440 AND "end_minute" > "start_minute"))
);
CREATE INDEX ON "tutor_availability_exceptions" ("tutor_profile_id", "date");
CREATE INDEX ON "tutor_availability_exceptions" ("date") WHERE "tutor_profile_id" IS NULL;

-- 2. A start date, so "Week 1" and "the first Monday" mean real dates. Nullable: existing rows keep working as they do now.
ALTER TABLE "mentoring_tutor_assignments" ADD COLUMN "start_date" DATE, ADD COLUMN "end_date" DATE;

-- 3. One occurrence cancelled or moved, without touching the rule that produces the others.
CREATE TYPE "TutorOccurrenceChange" AS ENUM ('CANCELLED', 'RESCHEDULED');
CREATE TABLE "mentoring_tutor_assignment_overrides" (
  "id" TEXT PRIMARY KEY,
  "assignment_id" TEXT NOT NULL REFERENCES "mentoring_tutor_assignments"("id") ON DELETE CASCADE,  -- as built: keyed by assignment, not session row
  "date" DATE NOT NULL,                          -- the occurrence being changed
  "original_start_minute" INTEGER NOT NULL,      -- as built: identifies which class of that day
  "kind" "TutorOccurrenceChange" NOT NULL,
  "new_date" DATE, "new_start_minute" INTEGER, "new_end_minute" INTEGER,
  "reason" TEXT NOT NULL,
  "created_by_user_id" TEXT NOT NULL,
  "created_at" TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE ("assignment_id", "date", "original_start_minute")
);
```

Why this and not a dated class table: a rule plus overrides is one booking system, so there is nothing to keep in step and no duplicate occurrences. Occurrences are worked out when a date is asked for. If reporting later needs stored occurrences, they can be materialised from the same rule.

Leave is not copied. The resolver reads approved rows of `employee_leave_requests` for the tutor's employee.

Not proposed now: a per-subject level table (`tutor_subject_grades`). The ten tutors have one level range for all their subjects, so the existing per-tutor levels are enough. It can be added later without changing anything above.

## 3. Engine changes (code, after the schema is approved)

1. **Resolve exact dates.** A student's subject schedule gets an optional `startDate`. The checker looks at the occurrences in the next eight weeks from it, so the Mentor sees a result per date: "9 Nov available, 10 Nov occupied (booked), 11 Nov occupied".
2. **A tutor's day is resolved in one order:** organisation holiday or approved leave closes the day; a special day off closes it; extra hours add to the weekly ranges; blocked time removes a range; classes are placed last. Cancelled occurrences are skipped and rescheduled ones are placed on the new date.
3. **Result codes** become: available, occupied, outside working hours, break, leave, holiday or non-working date, not working this day, availability not configured (reserved for a tutor with no hours at all), and blocked.
4. **Recurrence is checked on every date**, never the first one. A weekly class is refused if any one of its dates is taken.
5. **Assignment** keeps its transaction and row locks, rechecks every date, and flags (never deletes) classes that fall on a date a tutor becomes unavailable.
6. **Tutor calendar screen**: previous, next, today, a date picker, day and week views, with the states occupied, available, break, not working, leave or holiday, and not configured. The student on an occupied slot is shown as "Booked" to a Mentor and by name only to people who may see that student.

### Safety design of the script

- Refuses unless `DATABASE_URL` names exactly `elscore_os_staging` and a confirmation variable is set. A dry run is the default and `--execute` is required to write.
- Idempotent: every record is looked up by its natural key (e-mail, business id, unique constraint) and skipped if present, so a second run writes nothing.
- One transaction, all or nothing.
- **Rollback script:** removes only rows whose markers match (`@example.test` users, `EMP-SYNTH-`, `SYNTH-`) and the new-table rows created by the fixture user. It runs in a dry run first and prints counts before and after. It cannot touch the three existing tutors or any real record.
- It would not run in production: the name check fails.
